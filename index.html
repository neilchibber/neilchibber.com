UMD Loop

I lead the ten-plus engineers who build the electronics and firmware inside the University of Maryland's Mars rover. Every spring it goes to the Utah desert for the University Rover Challenge.

Hardware platform

Every subsystem board is split into a standard motherboard and a task-specific daughterboard. The motherboard carries the MCU and everything needed to run it. The daughterboard carries whatever the subsystem needs: servos, transceivers, sensors. Because every board shares the same MCU, the same firmware platform runs on all of them.

  1. STM32L476RGT6, a Cortex-M4 at 80 MHz
  2. USB port for power and debug
  3. Onboard debugger
  4. TCAN330 CAN transceiver
  5. TPS7A1901 regulator
  6. Power LED
  7. Oscillator
  8. Daughterboard connector
  9. LED solder bridge
  10. User LED
  11. Buttons

Why the L476. 1 MB of flash, 128 KB of RAM, and the peripherals the rover needs on one chip: CAN for the rover-wide network, timers and PWM for motors and servos, ADCs for analog sensors, and UART, SPI and I²C for everything else.

Zephyr firmware

Configuration, not code. main.c does nothing. Kconfig selects which systems a board runs, and the devicetree initializes the hardware and picks the drivers.

Generated boundaries. The CAN message database feeds an auto-generate step that produces each system's boundaries and message queues, so the protocol and the firmware cannot drift apart.

Systems are threads. Each system is a thread that reads its own message queue and talks to drivers. Zephyr gives every driver of the same kind the same API, so swapping a part does not change system code.

Stack sizing. The thread analyzer reports stack use and CPU time for every thread. The CAN receive thread peaks at 224 of 256 bytes and transmit at 184 of 256: enough headroom to run safely without wasting RAM on every board.

Radio link

The rover is driven from a base station over a radio link, and at competition that link has to hold up across open desert, behind terrain and at long range. I've started on it from both ends: getting the rover's networking stable, and designing a directional antenna for the base station.

Radio debugging. While testing the link I set a static IP on the Jetson, the rover's onboard computer, so it always sits at a known address. The base station can find the rover without discovery, and a dropped link is quick to spot.

I'm also in the process of getting my ham radio license.

Yagi-Uda antenna

In progress. This is a design plan, not a finished antenna.

Why a Yagi. The base station only needs to point toward the rover's operating area, so a directional antenna trades coverage it does not need for gain it does. One reflector, one driven element and five directors give a target of about 11 dBi.

What that buys. Against a plain dipole, 11 dBi is about 9 dB more signal, which in free space is roughly 2.8 times the range.

Projects

3-DOF robotic wrist controller

A custom KiCad PCB that controls a 3-DOF robotic wrist (pitch, yaw, roll) and its gripper. One board takes a single 24 V input and provides four DC motor channels with magnetic encoder feedback, two servo outputs, a laser diode output and an RS-485 link, all run by a plug-in STM32. I designed the board, wrote the firmware and tested it end to end.

Motor drive. Two L298N dual H-bridges give four independent DC motor channels: one for each wrist axis and one for the gripper. The L298N has no internal clamp diodes, so each driver has eight external flyback diodes to catch the inductive kick when a motor is switched off or reversed.

Feedback. Each motor connector carries both motor leads plus encoder power and two encoder signals, so one cable per joint handles drive and feedback.

Level shifting. Servo and laser outputs use an S8050 NPN driving an S8550 PNP, so a 3.3 V MCU pin can switch a 5 V load.

Firmware. C on the STM32 runs a PID position loop per axis, closing on real-time encoder feedback. On the assembled wrist it tracks within ±2° on all three axes.

Membrane tube extrusion control

At Alchemity, membrane tubes are extruded and dried in multi-hour runs. I built the closed-loop stepper controller that holds extrusion speed within 1% of target RPM for the whole run, so each tube keeps a uniform wall thickness, and the data acquisition system that records what the temperatures and motors did.

Sensing. Thermocouples land on quad amplifier boards that do cold-junction compensation and report temperature over I²C, so the microcontroller never handles microvolt signals directly.

Pipeline. A Python logger timestamps every sample, saves the run and generates the test report, which let us tune the extrusion parameters from data instead of by feel.

Ball mill relay controller

Ball milling a batch of powder at Alchemity takes days of unattended running. I built an ESP32-based relay controller in a custom enclosure that automates the mill, switching mains loads through solid-state relays on a schedule so nobody has to babysit it.

Switching. Solid-state relays switch the mains loads. With no contacts to wear or arc, they hold up to days of continuous cycling far better than mechanical relays.

A furnace that kept overshooting. A furnace running under PID control kept overshooting its setpoint. I traced it with a DMM to faulty relay outputs: the controller was asking the heater to turn off, and the relay stage was not following. I redesigned the relay control scheme and reprogrammed the alarm thresholds, which eliminated the fault.

SOFC thickness optimization tool

A Python GUI that picks the best material orientation and optimizes layer thickness to ±10 µm. Behind it is a MATLAB/Simulink model of the fuel cell (Nernst voltage, ohmic and activation losses) that shows how electrolyte and electrode thickness trade off against power output. MATLAB scripts parse the experimental data and feed the model.
